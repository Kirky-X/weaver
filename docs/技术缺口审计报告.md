## ⚠️ 与 LLM 优化方案直接相关的 4 条

这几条会影响 `docs/LLM调用优化方案.md` 的结论，**实施前必须先处理**。

### 1. 原定的验证方法失效

方案 §9.3 建议用 `llm_call_total{call_point}` 验证优化效果。**但该指标零调用**：

```
grep -rn "llm_call_total\|llm_call_latency" src --include=*.py | grep -v metrics.py
→ 空
```

`metrics.py:27/32/38` 三个 LLM 指标（调用数、延迟、fallback）**定义后从未被 `.inc()` / `.observe()`**。
→ **前置任务**：在 `src/core/llm/client.py` 实际请求返回/抛错处补埋点，否则优化前后无法量化对比。

### 2. 蒙特卡洛采样从未生效

`config/pipeline.toml` 的 `[monte_carlo]` 五项配置**全部作废**：

- `PipelineSettings`（`src/modules/processing/pipeline/config.py:58`）**没有 `monte_carlo` 字段**
- `model_config` 设了 `extra="ignore"`（`:74`）→ TOML 里的 `[monte_carlo]` 被静默丢弃
- `lifecycle.py:310` 读 `settings.pipeline.monte_carlo` → AttributeError
- `lifecycle.py:388` 用 `contextlib.suppress(Exception)` 把异常吞掉 → **MC sampler 永远为 None**

后果：`analyze.py:70` 的 `if len(body) > threshold and self._mc_sampler` 恒为 False。
→ **修正调用次数估算**：原估「长文 +1~2 次 LLM」实际不会发生，单篇调用上限应下调。

### 3. content_hash 缓存无失效机制

`content_hash_cache.py:38` TTL 7 天，命中即整篇跳过 P1+P3（0 次 LLM）。
→ **上线合并 prompt 前必须清 `content_hash:*` 键，或把 prompt 版本号并入缓存 key**，否则 7 天内新旧结果混杂，A/B 对比数据被污染。

### 4. CallPoint 覆盖率只有 13/24

`config/llm.toml` 只配了 13 个调用点，`CallPoint` 枚举有 24 个。缺配的 11 个（含 `RERANK`、`QUERY_EXPANDER`、`BRIEFING`、`ENTITY_RESOLVER`、`SEARCH_LOCAL`、`SEARCH_GLOBAL`、`COMMUNITY_TITLE`、`CAUSAL_INFERENCE` 等）走 `router.py:61` 会**直接抛 ValueError**。
→ 新增 `ANALYZE_NARRATIVE` 必须同步配置，否则 100% 崩溃（详见优化方案 §3.6）。
