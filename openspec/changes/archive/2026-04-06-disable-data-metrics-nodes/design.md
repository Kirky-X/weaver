## Context

Weaver 是一个新闻知识图谱系统，从新闻文章中提取实体（人物、组织机构、地点、事件、数据指标、法规与政策）及其关系。"数据指标"类型实体来源于 spaCy NER 的 `CARDINAL`、`PERCENT`、`MONEY` 标签，表示新闻中的数值数据。

当前实体提取流程：
1. **Phase 1**: spaCy NER 提取初步实体
2. **Phase 3**: LLM 精炼并补充实体
3. **Resolver**: 实体解析入库

现有配置系统使用 `pydantic-settings`，环境变量前缀 `WEAVER_`，嵌套分隔符 `__`。

## Goals / Non-Goals

**Goals:**
- 提供布尔配置项控制是否提取/存储"数据指标"实体
- 在三个提取阶段（spaCy、LLM、Resolver）都添加过滤检查
- 保持向后兼容，默认行为不变（允许数据指标实体）

**Non-Goals:**
- 不支持禁用其他实体类型（仅数据指标）
- 不修改已有数据指标实体的存储结构
- 不添加动态实体类型配置（仅静态配置）

## Decisions

### 决策 1: 配置结构

**选择**: 创建独立的 `EntitySettings` 配置类

**备选方案**:
- A) 独立 `EntitySettings` 类 ✅（选中）
- B) 添加到 `Settings` 根级别
- C) 添加到现有 `DedupSettings` 类

**理由**:
- 实体提取有独立的配置关注点
- 未来可能添加更多实体相关配置
- 与项目现有的嵌套配置风格一致

**环境变量**: `WEAVER_ENTITY__DISABLE_DATA_METRICS_NODES=true`

### 决策 2: 过滤位置

**选择**: 三阶段都添加检查

**备选方案**:
- A) 仅 spaCy 阶段
- B) 仅 Resolver 阶段
- C) 三阶段都添加 ✅（选中）

**理由**:
- spaCy 阶段拦截可节省后续处理开销
- LLM 阶段过滤确保 LLM 补充的实体也被处理
- Resolver 阶段作为最后一道防线

### 决策 3: Resolver 过滤与现有逻辑的关系

**选择**: 配置检查优先于字符串检查

**实现**: 当 `entity_type == "数据指标"` 时：
1. 先检查配置 `disable_data_metrics_nodes`
2. 若启用，直接返回跳过结果
3. 若未启用，继续执行现有的 `_looks_like_metric_string` 检查

**理由**: 配置是更高层面的开关，应优先判断

## Risks / Trade-offs

**风险**: 配置启用后，已存在的数据指标实体不会自动删除
→ **缓解**: 这是预期行为，用户需要手动清理或接受存量数据

**风险**: 用户可能误配置导致意外行为
→ **缓解**: 配置项命名清晰，文档说明用途，默认值保守（False）

**权衡**: 三阶段检查有少量代码重复
→ **接受**: 重复代码量很小，各阶段语义独立，维护成本可控
