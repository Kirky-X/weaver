## Context

Weaver 是一个内容聚合和知识图谱系统，需要爬取外部 URL 获取内容。当前 SSRF 防护仅阻止对私有网络的请求，无法识别恶意 URL。本设计引入多层安全检查机制，在请求发出前评估 URL 风险。

**约束**:
- 复用现有 HttpxFetcher 进行 HTTP 请求
- 使用现有 Redis 基础设施进行缓存
- 不影响正常业务请求的延迟

## Goals / Non-Goals

**Goals:**
- 实现 API 优先策略：URLhaus API 配置时优先使用，失败自动回退本地检查
- 实现本地检查：PhishTank 黑名单 + 启发式检测 + SSL 验证
- 实现差异化缓存：安全结果 6 小时，恶意结果 15 分钟
- 保持代码可测试性，每个检查器可独立测试

**Non-Goals:**
- 不实现 URLhaus 离线库（无官方离线数据源）
- 不集成其他第三方安全服务（如 VirusTotal、Google Safe Browsing）
- 不实现证书透明度日志查询（需要外部服务，增加延迟）
- 不修改现有爬取流程，仅在 URL 验证阶段增强

## Decisions

### 1. 分层架构 vs 单文件增强

**决策**: 采用分层架构，将检查器独立为子模块

**理由**:
- 职责分离，便于测试和维护
- 每个检查器可独立启用/禁用
- 新增检查器时无需修改核心逻辑

**替代方案**:
- 单文件增强：改动最小，但文件会膨胀到 800+ 行
- 插件架构：过度设计，当前需求不需要动态加载

### 2. API 检查策略

**决策**: API 安全时跳过本地检查，但仍执行 SSL 验证

**理由**:
- URLhaus 数据权威性高于本地启发式
- SSL 验证独立于 URL 恶意性，仍有价值
- 减少不必要的计算开销

**替代方案**:
- 并行检查：增加延迟，无额外收益
- 完全跳过：错过 SSL 问题检测

### 3. PhishTank 数据源选择

**决策**: 使用 PhishTank 作为本地黑名单数据源

**理由**:
- 免费且无需 API key
- 提供完整 JSON 数据下载
- 社区驱动，更新频繁

**替代方案**:
- OpenPhish：数据量较小
- Google Safe Browsing：需要 API key，有配额限制
- 自建黑名单：维护成本高

### 4. 缓存存储选择

**决策**: 使用 Redis 存储

**理由**:
- 项目已有 Redis 基础设施
- 支持 TTL 自动过期
- 分布式环境共享缓存

**替代方案**:
- 内存缓存：单进程，重启丢失
- 文件缓存：性能差，需处理并发

## Risks / Trade-offs

**风险 1: PhishTank 同步失败**
→ 缓解: 保留本地数据文件，下次启动时重试

**风险 2: URLhaus API 速率限制**
→ 缓解: 自动回退本地检查，记录警告日志

**风险 3: 误判导致正常 URL 被拦截**
→ 缓解: 使用风险等级而非二元判断，LOW/MEDIUM 记录日志但不强制拦截

**风险 4: SSL 验证增加延迟**
→ 缓解: 设置 10 秒超时，失败时返回 LOW 风险而非阻塞

**风险 5: 编码绕过检测**
→ 缓解: 启发式检测使用双重解码，检测常见编码混淆模式
