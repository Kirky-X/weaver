## Context

Weaver 使用 FastAPI + uvicorn 运行，端口配置在 `APISettings.port`（默认 8000）。当前启动流程直接使用配置端口，若端口被占用则 uvicorn 会报错退出。需要在不改变现有架构的前提下，在配置加载阶段自动解析可用端口。

**约束条件**：
- 使用 Python 标准库（socket），不引入新依赖
- 端口解析在 Settings 初始化时完成，对上层透明
- 支持本地开发（127.0.0.1）和 Docker 部署（0.0.0.0）两种场景

## Goals / Non-Goals

**Goals:**
- 应用启动时自动检测配置端口是否可用
- 端口被占用时双向搜索找到可用端口（优先向上递增）
- 通过日志、.env 文件、Prometheus 指标公告实际端口
- 支持通过配置禁用端口自动检测
- Docker 容器内 healthcheck 能正确检测动态端口

**Non-Goals:**
- 不支持特权端口（<1024）的自动分配
- 不处理端口释放后的重新绑定
- 不实现跨进程的端口协调（假设单实例运行）

## Decisions

### 1. 端口检测时机：Settings 初始化阶段

**选择**：在 `APISettings.__init__()` 中调用 `_resolve_port()`

**理由**：
- 端口是配置的一部分，在配置加载时就确定最合理
- 确保所有依赖端口的组件使用一致的值
- 便于单元测试（可 mock socket 操作）

**替代方案**：
- 在 `main()` 入口处检测：需要额外传播端口变更，增加复杂度
- 在 Container 初始化时检测：服务初始化顺序可能已使用原端口

### 2. 端口搜索算法：双向搜索

**选择**：优先向上递增，再向下递减（8000 → 8001 → 7999 → 8002 → 7998...）

**理由**：
- 向上递增更直观，通常是用户期望的方向
- 双向搜索在端口密集使用时能更快找到可用端口
- 限制搜索范围 1024-65535，避免特权端口

**替代方案**：
- 仅向上搜索：在高端口区域可能搜索更久
- 随机搜索：不可预测，不利于调试

### 3. 端口公告方式：多通道

**选择**：日志 + .env 文件 + Prometheus 指标

**理由**：
- 日志：开发人员能立即看到实际端口
- .env 文件：其他进程/脚本能读取实际端口
- Prometheus 指标：监控系统能发现端口变更

**替代方案**：
- 仅日志：Docker healthcheck 无法获取动态端口
- 仅文件：开发时需要额外查看文件

### 4. 错误处理：启动失败

**选择**：在 `max_attempts` 内未找到可用端口时抛出 `PortExhaustionError`，应用启动失败

**理由**：
- 无可用端口是严重错误，不应静默降级
- 用户需要知道问题并采取行动（释放端口或调整配置）

## Risks / Trade-offs

### Risk: 端口竞争条件
**描述**：检测可用后、实际绑定前，端口可能被其他进程占用
**缓解**：时间窗口极小（毫秒级），且 uvicorn 绑定失败会报错，用户可重试

### Risk: .env.weaver 文件残留
**描述**：异常退出后，`.env.weaver` 可能包含过期端口信息
**缓解**：每次启动时覆盖写入；healthcheck 同时验证服务健康状态

### Risk: Docker 容器内端口冲突
**描述**：容器内端口冲突较少见，但仍可能发生
**缓解**：功能默认启用，支持 `PORT_AUTO_DETECT=false` 禁用

### Trade-off: 搜索延迟 vs 可靠性
**描述**：搜索更多端口增加启动延迟，但提高找到可用端口的概率
**选择**：默认 100 次尝试，用户可通过 `port_max_attempts` 调整
